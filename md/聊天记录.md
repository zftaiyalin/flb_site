你看到的这个错误：

Route Error (400 Invalid content type: text/html; charset=UTF-8)
意思是：

你调用的 API 或路由期望收到 JSON 或特定 Content-Type 的请求体

但是你发送了 text/html; charset=UTF-8

所以服务器返回 400 错（Bad Request），提示“Content-Type 不对”

常见原因
前端请求头没设置正确

Content-Type: application/json
如果你用 fetch / axios / curl，需要明确指定。

fetch 示例：

fetch('https://api.example.com/route', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': 'Bearer YOUR_TOKEN'
  },
  body: JSON.stringify({ key: 'value' })
})
后端期望 JSON，但你发送了表单或 HTML

可能你在 Postman 或浏览器直接访问 URL，返回的是 HTML 错误页

这种情况下 API 会提示 content type 错误

代理 / 网关返回了 HTML

比如 Nginx / Cloudflare / 企业代理

API 请求被拦截或重定向，返回 HTML 页面

所以客户端收到 text/html → 不符合 API 预期 → 400

排查方法
确认 URL 是否正确

不要直接访问浏览器，API URL 通常只接受 POST/GET 请求

确认 Content-Type

必须和 API 文档一致（一般是 application/json）

打印请求 / 响应头

确认是不是被重定向或者代理返回 HTML

避免 GET 发送 body

某些 API 对 GET 请求带 body 会报错

💡 总结

错误本质：API 收到你发送的 HTML 内容，而它只接受 JSON 或指定格式

解决办法：确保请求体是 JSON，Content-Type: application/json，URL 和方法正确。

3️⃣ 使用脚本或工具（半自动）
如果你有 官方 JSON 导出，可以写个 Python 脚本：

import json

with open('chat_export.json', 'r', encoding='utf-8') as f:
    data = json.load(f)

for conv in data['conversations']:
    date = conv['created_at'][:10]
    for i, message in enumerate(conv['conversation']):
        role = message['role']
        content = message['content']
        filename = f"{date}_{i}_{role}.md"
        with open(filename, 'w', encoding='utf-8') as f_out:
            f_out.write(f"**{role}**:\n{content}")

发现规律了：用 IP 直连成功，用域名（带 SNI）就失败。可能是 nginx 1.31.1 + OpenSSL 3.5.6 的 ML-KEM（后量子密钥交换）协商问题。在 nginx.conf 里显式限制密钥交换组来修复。

这个判断方向是对的：IP 直连绕过 SNI/域名证书链，域名失败就很像 TLS 握手阶段的问题，而不是应用层问题。

已思考 6s
对，直接在 server {} 里加这个最稳：

ssl_conf_command Groups X25519:secp256r1:secp384r1;
完整位置示例：

server {
    listen 443 ssl http2;
    server_name your-domain.com;

    ssl_certificate /path/fullchain.pem;
    ssl_certificate_key /path/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;

    # 关键：禁用 OpenSSL 3.5 默认优先的 ML-KEM / hybrid PQC groups
    ssl_conf_command Groups X25519:secp256r1:secp384r1;

    ...
}
然后执行：

sudo nginx -t
sudo systemctl reload nginx
OpenSSL 3.5 默认支持并偏向 PQC/ML-KEM 相关 TLS groups，这是可能触发兼容问题的点；ssl_conf_command Groups ... 可以显式限制 TLS groups。
